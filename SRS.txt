DOCUMENT CONTROL
1. Purpose of This Document
This document defines the complete requirements, expected behaviour, modules, user roles, business rules, workflows, data requirements, technical architecture and development guidelines for the Sadhana Report Management System.
It is intended to serve as the central reference for:
1.	Understanding what the project is supposed to do.
2.	Developing the frontend and backend.
3.	Designing the database.
4.	Implementing user roles and permissions.
5.	Testing the application.
6.	Maintaining the application after deployment.
7.	Resuming development after a break without losing project context.
Important: This document describes the intended system. It does not mean that the features have already been implemented.
2. Project Overview
The Sadhana Report Management System is a web-based application designed for ISKCON devotees to record, manage, review and analyse their daily spiritual practices.
The application will allow devotees to submit daily Sadhana Reports containing information about their daily routine, Japa, reading, devotional activities, chanting quality, sleep schedule, spiritual discipline and other activities.
Counsellors will be able to monitor the progress of their assigned devotees. Senior Devotees will receive limited read-only access to the devotees assigned to them. Administrators will manage users, permissions, reports, assignments, system settings and backups.
The application will maintain historical records and provide reports, graphs, progress scores, PDF downloads and Excel exports.
The system should be designed for long-term use, with the possibility of supporting multiple Counsellors and a growing number of devotees.
3. Problem Statement
Managing daily Sadhana information manually can create several problems:
•	Devotees may forget to submit their daily reports.
•	Counsellors may find it difficult to monitor multiple devotees.
•	Historical Sadhana information may be scattered across different files or spreadsheets.
•	Manual calculations of Japa, reading and other activities can be time-consuming.
•	Weekly and monthly progress comparisons may require manual work.
•	Data may be lost when reports are maintained only in local files.
•	Managing assignments and permissions becomes difficult as the number of devotees increases.
The proposed system aims to solve these problems through a centralized digital platform.
4. Project Objectives
The main objectives are:
1.	Provide a simple platform for daily Sadhana report submission.
2.	Maintain accurate historical records of devotees.
3.	Make Japa tracking easier.
4.	Monitor daily, weekly and monthly Sadhana progress.
5.	Allow Counsellors to guide their assigned devotees.
6.	Provide limited and controlled Senior Devotee access.
7.	Give Administrators centralized management facilities.
8.	Generate useful reports and analytics.
9.	Automate Excel data updates.
10.	Maintain automatic database backups.
11.	Protect individual devotee information.
12.	Support mobile and desktop usage.
13.	Keep the architecture expandable for future requirements.

6. STAKEHOLDERS AND USER ROLES
The system will support four primary roles.
6.1 Administrator
The Administrator is responsible for managing the entire application.
The first Administrator will be the project owner.
Admin responsibilities
1.	Create devotee accounts.
2.	Manage user accounts.
3.	Assign Counsellors.
4.	Assign Senior Devotees.
5.	Manage user roles.
6.	View all devotees.
7.	View all reports.
8.	View complete historical records.
9.	View individual and overall analytics.
10.	Manage system settings.
11.	Manage spiritual activities.
12.	Manage account requests.
13.	Review requests requiring Admin approval.
14.	Generate PDF and Excel reports.
15.	Manage master Excel data.
16.	Monitor database backup status.
17.	Restore the database from backups.
18.	Suspend and reactivate accounts according to the approval rules.
Admin account requirements
The project owner will have:
•	Admin role.
•	Devotee role.
•	A separate Counsellor assigned to their Devotee account.
The same person must be able to use Admin and Devotee functionality without needing two unrelated login accounts.
The application should support multiple roles for a single user account.
6.2 Devotee
A Devotee is the primary user who submits daily Sadhana information.
Devotee permissions
1.	Log in securely.
2.	View and edit their permitted profile information.
3.	Submit daily Sadhana Reports.
4.	View their own reports.
5.	Edit a report within the permitted editing period.
6.	View missing reports.
7.	Copy the previous day's report as a starting point.
8.	Preview a report before submission.
9.	View Japa history.
10.	View Sadhana activities.
11.	View daily, weekly and monthly progress.
12.	View progress graphs.
13.	Download their own reports.
14.	View website notifications.
15.	Submit applicable requests.
16.	Request a Counsellor change.
Devotee privacy
A Devotee must not be able to access another Devotee's private reports, personal details or progress information.
6.3 Counsellor
A Counsellor guides a group of assigned devotees.
Counsellor permissions
1.	View assigned devotees.
2.	View assigned devotees' profiles.
3.	View assigned devotees' daily reports.
4.	View complete available report history.
5.	View individual progress.
6.	View assigned devotees' analytics.
7.	Filter reports by date and devotee.
8.	View missing reports.
9.	Respond to applicable requests.
10.	Participate in approval workflows where required.
11.	Request a report correction from a Devotee.
Counsellor restrictions
•	Cannot view unrelated devotees.
•	Cannot assign themselves to devotees.
•	Cannot directly edit a Devotee's submitted report.
•	Cannot access Admin-only settings.
•	Cannot download or export information outside their permitted scope.
Recommended correction process: A Counsellor can identify an incorrect report and request a correction. The Devotee reviews and submits the corrected information. The system preserves the original submission information where technically appropriate.
6.4 Senior Devotee
A Senior Devotee receives limited access to support assigned devotees.
Recommended permissions
1.	View assigned devotees.
2.	View assigned devotees' reports.
3.	View assigned devotees' progress.
4.	View available report history.
5.	Use permitted filters.
Restrictions
•	Read-only access.
•	Cannot edit reports.
•	Cannot delete reports.
•	Cannot assign Counsellors.
•	Cannot manage user accounts.
•	Cannot access unrelated devotees.
•	Cannot modify system settings.
The Senior Devotee should only see information explicitly included in their assigned access.

7. ACCOUNT MANAGEMENT AND REGISTRATION
7.1 Account Creation
The Administrator will create new Devotee accounts.
The registration process should work as follows:
1.	Admin opens the User Management section.
2.	Admin selects Create New Devotee.
3.	Admin enters the required initial information.
4.	The system creates the account.
5.	The system generates an invitation link or temporary password.
6.	The Devotee receives the account invitation.
7.	The Devotee opens the invitation.
8.	The Devotee completes the remaining profile information.
9.	The Devotee sets a permanent password.
10.	The account follows the configured approval process.
11.	The account becomes active after all required approvals.
7.2 Login
The system should support login using:
•	Email address and password.
•	Mobile number and password.
Only one account should be associated with a particular email address.
The system must validate login credentials securely.
7.3 Password Management
The system should support:
•	Secure password storage.
•	Password change.
•	Forgot password.
•	Email password-reset link.
•	Password confirmation.
•	Appropriate password validation.
•	Session management.
Passwords must never be stored as plain text.
7.4 Profile Management
A Devotee should be able to edit permitted profile details.
The system should support controlled changes to sensitive fields.
Previously discussed account rules include:
•	Email changes require Admin approval.
•	Mobile number changes require OTP verification.
•	Duplicate accounts can be merged by Admin.
•	Suspended accounts require Admin permission for access.
•	Historical reports remain available after account closure.
•	Account reactivation follows Counsellor approval.
•	Account deletion requests are reviewed by Admin.
•	Multiple-device login is permitted.
These account-management rules should be retained in the implementation plan and verified against the final account workflow before coding.
7.5 Account Status
Recommended account statuses:
•	Invitation Pending
•	Profile Incomplete
•	Pending Approval
•	Active
•	Suspended
•	Closure Requested
•	Closed
The application should prevent unauthorized login and access based on account status.
7.6 Duplicate Accounts
The system should prevent duplicate email registration.
Admin should have a controlled facility to merge duplicate accounts where necessary.
Historical reports must remain correctly associated with the surviving account.

8. DAILY SADHANA REPORT MODULE
This is the central module of the entire application.
8.1 Purpose
The Daily Sadhana Report module allows each Devotee to record their daily spiritual practices.
Each Devotee should normally submit one main report per day.
8.2 Report Sections
The report should contain the following sections.
A. Daily Routine
Fields:
•	Report Date.
•	Wake-up Time.
•	Sleep Time.
The system should validate time values.
The report date should be based on the application's configured timezone.
B. Japa Information
Fields:
•	Total Rounds.
•	Total Japa Duration.
•	Japa Start Time or Session Times, where applicable.
•	Japa End Time or Session Times, where applicable.
•	Japa Quality.
Japa Quality options:
•	Low
•	Medium
•	High
The report should support multiple Japa sessions in one day.
The final daily Japa total should combine the sessions.
C. Reading Information
Fields:
•	Reading Completed: Yes/No.
•	Book Name.
•	Reading Duration.
The system should allow the Devotee to select or enter the relevant book name.
The book name should be maintained consistently for reporting.
D. Seva Information
Fields:
•	Seva Type.
•	Seva Duration.
•	Completion Status.
The system should support recording different kinds of devotional service.
E. Morning Worship
Morning worship should be recorded as a combined section rather than requiring many unnecessary separate entries.
The exact individual activities included in this section should be finalized during the form design.
F. Four Regulative Principles
The report should include tracking for the four regulative principles.
Each principle should have an appropriate completion or adherence field.
A notes field should be available where required.
The interface should avoid unnecessarily complicated inputs.
G. Satsanga
Field:
•	Satsanga: Yes/No.
H. Lecture
Fields:
•	Lecture Attended: Yes/No.
•	Lecture Duration.
•	Lecture Topic.
•	Speaker Name.
I. Bhakti Time
The system should calculate or display time spent on selected devotional activities where the required data is available.
Avoid double-counting the same activity duration.
J. Realization
A text area should be available for the Devotee to write personal spiritual realizations or reflections.
This field should support normal text entry.
8.3 Report Submission Rules
1.	A Devotee can submit one main report for each date.
2.	Duplicate submissions for the same date should be prevented.
3.	The Devotee should be able to preview the report before submission.
4.	The system should validate mandatory fields.
5.	The system should identify incomplete reports.
6.	The system should show a clear submission confirmation.
7.	A successful submission should update the Devotee's report history.
8.	A successful submission should trigger the Master Excel update process.
8.4 Report Editing Rules
A submitted report can be edited within 24 hours of submission.
After the 24-hour period, normal editing should be disabled.
The system should clearly show whether a report is editable.
The application should retain relevant submission timestamps.
A report correction requested by a Counsellor should follow the controlled correction process.
8.5 Late Submission
Late report submission is not allowed under the current requirements.
If a report is not submitted within the permitted reporting period:
•	The date should appear as Missing.
•	The system should not silently create a report.
•	The Devotee should see the missing date in their report history.
•	The system should send a reminder if the reminder conditions are satisfied.
The exact daily reporting deadline and timezone must be configured before implementation.
8.6 Copy Previous Report
The Devotee should have an option to copy the previous day's report.
The copied information should be inserted as a draft.
The Devotee must review the information before submitting.
The copied report must not be submitted automatically.
8.7 Report Status
Recommended report statuses:
•	Not Started
•	Draft
•	Submitted
•	Edited
•	Missing
•	Correction Requested
•	Corrected
The system should use these statuses consistently in dashboards and reports.

9. JAPA TRACKING MODULE
9.1 Purpose
This module tracks the Devotee's daily chanting activity.
It should be simple and should not require the Devotee to record every individual Mala.
9.2 Japa Dashboard
The Japa Dashboard should display:
•	Daily Japa Target.
•	Total Rounds Completed.
•	Remaining Rounds.
•	Completion Percentage.
•	Total Japa Duration.
•	Japa Sessions.
•	Japa History.
9.3 Multiple Japa Sessions
The Devotee may chant at different times throughout the day.
Example:
Session	Start Time	End Time	Rounds
Morning	5:00 AM	6:30 AM	8
Afternoon	2:00 PM	2:30 PM	4
Evening	7:00 PM	7:30 PM	4
Total	—	—	16
The application should calculate:
•	Total rounds.
•	Total duration.
•	Remaining target.
•	Target completion percentage.
These values are illustrative examples, not fixed targets.
9.4 Japa Target
Each Devotee should have an individual Japa target.
The target should be changeable through the permitted system process.
The application should calculate:
Completion Percentage = (Completed Rounds / Daily Target) × 100
If the target is zero or missing, the system must avoid division errors and display an appropriate status.
If the Devotee does not meet the target, the application should display the achieved percentage.
9.5 Japa History
The Devotee should be able to view:
•	Daily Japa history.
•	Weekly Japa history.
•	Monthly Japa history.
•	Calendar view.
•	List view.
•	Date filters.
9.6 Excluded Features
The initial version will not include:
•	Live Japa counter.
•	Individual Mala recording.
•	Automatic tracking of physical chanting activity.
The Devotee will enter the completed total after chanting.

1.	Devotee submits a Counsellor Change Request.
2.	System creates a request record.
3.	Admin receives a notification.

5.	Admin approves or rejects it.
6.	If approved, Admin assigns a new Counsellor.
7.	System updates the current assignment.
8.	System preserves previous assignment history.
9.	Relevant users receive a notification.
The old and new Counsellors do not need to approve the request unless this policy is changed later.
11.7 Report Correction
Counsellors should not directly modify submitted reports.

1.	Counsellor identifies the incorrect information.
2.	Counsellor submits a correction request.
3.	Devotee receives a notification.
4.	Devotee reviews the correction.
5.	Devotee edits and resubmits the permitted information.
6.	System updates the report and its applicable status.

17. EXCEL AUTOMATION MODULE
17.1 Purpose
The application should maintain one centralized Master Excel File containing all devotees' report information.
17.2 Master Excel File
The Master Excel File should contain all permitted report data in a consistent structure.
Recommended sheets:
1.	Devotee Master.
2.	Daily Sadhana Reports.
3.	Japa Records.
4.	Spiritual Activities.
5.	Counsellor Assignments.
6.	Summary Data.
The sheets should have stable column names and clear identifiers.
17.3 Automatic Update
Whenever a Devotee successfully submits a report:
1.	Backend saves the report in MySQL.
2.	Backend confirms the database transaction.
3.	An Excel update task is triggered.
4.	The new or updated report is reflected in the Master Excel File.
5.	The system records whether the export update succeeded.
6.	If the update fails, the system retries or queues the operation.
Important technical rule: MySQL must be the primary source of truth. Excel is an export and reporting copy, not the main database.
The report should not be lost if Excel updating fails.
17.4 Duplicate Prevention
The system should identify each report using a stable report ID.
Updating the Master Excel File must not create duplicate rows when the same report is processed again.
17.5 Excel Failure Handling
If Excel updating fails:
•	The database report must remain saved.
•	The failure should be recorded in a technical log.
•	The system should retry the update.
•	Admin should be able to see the export status.
•	The system should support rebuilding the Excel file from MySQL.

•	Additional weekly backup.
18.3 Backup Requirements
The system should:
1.	Create automatic backups.
2.	Store backups separately from the main database.
3.	Protect backup access.
4.	Retain backup files according to a defined retention policy.
5.	Monitor backup completion.
6.	Notify Admin about backup failures.
7.	Support restoration from a valid backup.
18.4 Full Database Restoration
If data is accidentally deleted or the database is damaged:
1.	Admin initiates the restoration process.
2.	The system identifies the selected backup.
3.	The backup is validated.
4.	Restoration is performed in a controlled environment.
5.	Database consistency is checked.
6.	The restored application is verified.
Critical: A full restoration may replace newer data with older backup data. Therefore, restoration must be a protected operation with a confirmation step and, where possible, a snapshot of the current database before restoration.
18.5 Backup Testing
A backup is not considered reliable merely because a file exists.
The development and maintenance process should include periodic restoration tests.

•	Application errors.
•	Authentication failures.
•	Database failures.
•	Backup failures.
•	Excel export failures.
•	Critical system exceptions.
Technical logs must not be confused with a full Admin Activity Audit Log.

36. FINAL PROJECT VISION
The Sadhana Report Management System should become a reliable, secure and easy-to-use platform for managing the daily spiritual practices of ISKCON devotees.
It should help devotees maintain their daily Sadhana records, understand their own progress and maintain consistency.
It should help Counsellors guide assigned devotees through accurate historical information and progress summaries.
It should help Senior Devotees monitor assigned devotees within controlled permissions.
It should help Administrators manage accounts, reports, requests, assignments, analytics and backups from one centralized platform.
The system should prioritize:
•	Simplicity for Devotees.
•	Useful information for Counsellors.
•	Restricted access for Senior Devotees.
•	Complete management facilities for Admin.
•	Privacy and security.
•	Accurate historical records.
•	Reliable backups.
•	Maintainable code.
•	Future scalability.
The goal is not merely to build a form for submitting daily reports. The goal is to build a complete Sadhana management platform that can be maintained and expanded over time.
